To design a fair and effective **AI Co-Judge system**, you should treat the AI as an **auditor and evidence collector**, rather than an autonomous decision-maker. A naive "LLM Judge" that is simply given a GitHub repo and pitch deck will be easily tricked by polished prose, verbose documentation, or slick slide design.

The standard architecture separates **objective fact-checking** (code audits and deck extraction) from **subjective scoring**, providing human judges with verified evidence and transparent scoring rationale.

---

## 1. System Architecture Overview

```
[ Pitch Deck PDF / Video ] ───► [ Multimodal Extraction Agent ] ──┐
                                                                 ├──► [ Claims-vs-Code Auditor Agent ] ──► [ Deterministic Scorer ] ──► [ Human Judge Dashboard ]
[ GitHub Repository ]     ───► [ Codebase Inspection Agent ]    ──┘

```

The system uses a **three-tier architecture**:

1. **Extraction & Inspection Agents:** Collect raw facts from slides, video transcripts, and the Git repository.
2. **Audit Engine:** Cross-references the claims made in the pitch against what actually exists in the codebase.
3. **Scoring Engine:** Applies a structured rubric deterministically, outputting scores alongside clickable file/line citations for human review.

---

## 2. Evaluation Pipeline Breakdown

### Phase A: Pitch Deck & Submission Analysis

* **Multimodal Slide Parser:** Convert presentation slides (PDF/PPTX) into structured text, extracting value propositions, architecture claims, feature lists, and tech stack declarations.
* **Demo Video Verification:** Transcribe the demo video (using Speech-to-Text) and perform keyframe analysis to verify if the UI/demo matches the pitch narrative.

### Phase B: Ground-Truth Codebase Auditing

Instead of passing the entire codebase to an LLM prompt, deploy a specialized **Code Agent** equipped with repository search tools (`grep`, directory walk, file AST analysis):

* **Commit History & Authenticity Check:** Inspect Git commit timestamps and diff sizes across the event timeframe to flag pre-built code or bulk copy-pasted boilerplate.
* **Claims Verification Engine:** Search for structural proof of claims made in the pitch.
* *Example Claim:* "Uses a custom retrieval pipeline with vector search."
* *Code Audit Check:* Searches imports for vector database SDKs (e.g., Pinecone, Qdrant, PGVector) and verifies actual query logic exists in the codebase.



### Phase C: Claim Mismatch Detection

The core innovation of a Co-Judge is flagging **"Pitch vs. Code Mismatches"**:

* **Supported Claim:** Feature pitched $\rightarrow$ Verified working code found with line numbers.
* **Exaggerated Claim:** Feature pitched as operational $\rightarrow$ Code reveals hardcoded mock JSON responses.
* **Ghost Claim:** Core value prop pitched $\rightarrow$ Zero corresponding code or API calls found in repository.

## 3. Rubric Design & Deterministic Scoring Rules

To prevent AI score hallucination or verbosity bias, enforce **low-precision binary or 3-point scales per dimension** and calculate total scores in application logic—not inside the LLM prompt.

| Evaluation Category | Evaluation Method | Scoring Anchor | Weight |
| --- | --- | --- | --- |
| **Technical Execution** | Code Audit Agent | **Pass (1.0):** Clean architecture, real API integration, working build.<br>

<br>**Partial (0.5):** Functional UI with heavy hardcoded/mocked backend.<br>

<br>**Fail (0.0):** Broken build or missing core code. | 35% |
| **Claim Integrity** | Mismatch Auditor | Ratio of verified pitch claims vs. unverified/ghost claims. | 25% |
| **Product Originality** | Semantic Vector Search | Distance metric comparing project description against past hackathon submission databases and open-source templates. | 20% |
| **Pitch & Problem Fit** | Deck Analysis Agent | Clarity of problem statement, defined target user, and feasibility of proposed solution. | 20% |

---

## 4. Designing for Fairness & Mitigating AI Bias

AI judges introduce inherent risks if not properly calibrated:

* **Prevent Prose & Formatting Bias:** Teams with expensive-looking slides or highly eloquent Readme docs often receive inflated scores from LLMs. Force the AI to grade **evidence first** (citations, code lines, working API routes) before assigning numerical values.
* **Decouple Multi-Dimension Calls:** Never ask an LLM to score "Originality, Code Quality, and Design" in a single prompt. Run individual agent calls for each dimension to prevent score leakage (where a great design anchors a high score for broken code).
* **Human-in-the-Loop Override ("Objection Button"):** Provide participants with a view of their AI Audit Report. If the AI misidentified a file or missed a backend route, allow a single "Objection Request" where human judges review the flagged citation.
* **Explainable Audits:** Every score generated by the AI Co-Judge must come with clickable file/line link citations so human judges can audit the AI's reasoning in under 30 seconds.
